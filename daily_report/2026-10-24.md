# FSSLK 작업 기록 — 2026-10-24

## 오늘 한 일

### 분산 작업과 네트워크 측정 개선

- 길이 접두 프레임으로 JSON 메타데이터와 텐서 바이너리를 전송하도록 구성했다. CPU `int64` 및 `float32` 텐서를 지원하고 프레임 크기를 64 MiB로 제한한다.
- Worker 시작 시 CPU 합산 처리량을 측정한다. Coordinator는 RTT와 jitter, 전송 처리량, UDP probe 패킷 손실률 및 연결 안정성을 수집해 `status`에서 보여준다.
- 측정된 CPU 성능과 RTT, 네트워크 처리량 및 손실률을 반영해 작업 청크를 나누는 결정적 스케줄러를 구현했다. 강화학습은 사용하지 않는다.
- Worker 연결이 끊기거나 작업이 실패·타임아웃되면 청크를 다른 Worker에 재시도하고, 최대 시도 횟수를 넘으면 요청을 실패 처리한다. 이전 시도의 늦은 응답은 무시한다.

### Docker별 네트워크 프로필

Compose에서 Worker마다 Linux `netem` 설정을 다르게 적용했다. 송신은 `eth0`, 수신은 IFB로 리다이렉트해 양방향을 모두 제한한다.

| Worker | 지연 | 속도 상한 | 패킷 손실 |
|---|---:|---:|---:|
| fast | 2 ms | 500 Mbps | 0% |
| medium | 25 ms | 50 Mbps | 1% |
| slow | 75 ms | 10 Mbps | 3% |

## 실행 및 검증

- `python -m unittest discover -s tests -v`: 테스트 21개 통과.
- `docker compose up --build -d`로 Coordinator와 세 프로필 Worker를 실행하고, `tc`에서 컨테이너별 qdisc 설정을 확인했다.
- 실행 중 `status`에서 확인한 네트워크 측정값:

| Worker | RTT | 측정 처리량 | UDP 패킷 손실 |
|---|---:|---:|---:|
| fast | 5.19 ms | 86.22 Mbps | 0% |
| medium | 56.27 ms | 8.03 Mbps | 1% |
| slow | 332.20 ms | 0.42 Mbps | 6.5% |

  처리량은 설정한 속도 상한이 아니라 지연과 손실을 포함한 애플리케이션 probe 측정값이며, 실행 시점에 따라 달라질 수 있다. 손실률도 UDP echo 경로의 표본 측정값이다.
- 1,000,000개 원소의 분산 합산 결과 `499999500000`이 기대값과 일치했고, 세 Worker가 모두 참여했다.
- `git diff --check`를 통과했다. 검증 후 `docker compose down`으로 클러스터를 종료했고, `docker compose ps --all`에서 실행 중인 컨테이너가 없음을 확인했다.

## 현재 제한 사항

- 패킷 손실은 UDP probe로 측정한다. TCP 데이터의 전송 복구는 TCP 자체 재전송에 맡기며, 애플리케이션 수준 재시도는 현재 stateless `sum` 작업의 청크 단위로 동작한다.
- 스케줄러는 현재 측정치를 사용하는 휴리스틱이다. 손실에 따른 처리량 보정도 단순 모델이므로 실제 작업과 네트워크 환경에 맞춘 보정이 필요하다.
- 인증과 암호화는 구현하지 않았다.

## `pipeline-exec` 브랜치 검증 (아직 `main`에 미병합)

- `origin/pipeline-exec`의 `28c684c`를 별도 clone에서 확인했다.
- 변경분은 캡처 그래프를 허용된 PyTorch 연산 목록으로 직렬화하고, 두 stage로 나눠 Worker에 정의와 가중치를 배포한 뒤 activation을 마이크로배치로 흘려보내는 기능이다. Coordinator는 stage 요청을 지정 Worker에 전달하며, CLI에 `run-pipeline`을 추가했다.
- 해당 브랜치에서 `python -m unittest discover -s tests -v`를 실행해 44개 테스트가 통과했다. Docker Compose로 실제 coordinator와 Worker 3개도 올렸고 모두 `active`로 등록됐다.
- 컨테이너 hostname을 Worker ID로 사용해 기본 데모 모델(4 layers, dim 512, heads 8, batch 8, sequence 256)을 실행했다. m1과 m4 모두 결과 검증을 통과했다.

| 마이크로배치 수 | 실행 시간 3회 | 중앙값 | 로컬 기준 1/2 thread | 최대 절대 오차 |
|---:|---|---:|---:|---:|
| 1 | 21.64 / 20.51 / 21.80 s | 21.64 s | 1.12 / 0.66 s | `1.192e-06` |
| 4 | 22.08 / 22.67 / 20.45 s | 22.08 s | 1.10 / 0.68 s | `1.192e-06` |

- 이 측정에서는 m4가 m1보다 빨라지지 않았다. m4 실행 중 medium Worker의 링크 probe가 RTT 약 8.1 s, 대역폭 2.9 Mbps로 측정됐고, 예측 시간 57.21 s와 실제 중앙값 22.08 s도 차이가 컸다. 실행 성능을 결론내리기 전에 네트워크 측정과 예측 모델을 더 검증해야 한다.
- 추가로 m1 파이프라인의 stage/가중치 배포와 warm-up을 마친 뒤 측정 실행 구간에 medium Worker의 `eth0`와 `ifb0` 손실을 1%에서 10%로 올려 단일 실행을 했다. 실행은 성공했고 149.87 s가 걸렸으며, 최대 절대 오차는 그대로 `1.192e-06`이었다. medium stage의 wall time은 149.23 s, 그중 연산은 0.44 s였다. 테스트 후 양방향 손실을 Compose 기본값 1%로 복구했다.
- 이 실행의 `links` 값(RTT 55.46 ms, 4.29 Mbps, 손실 1.7%)은 손실을 10%로 바꾸기 전에 수집된 snapshot이다. 따라서 이 값과 17.90 s 예측은 10% 구간을 반영하지 않는다. 실행 시간은 기본 m1 중앙값 21.64 s보다 크게 늘었지만 파이프라인은 실패 없이 완료됐고, 출력 비교 오차는 `1.192e-06`이었다.
- 실행 JSON은 coordinator 컨테이너의 `/tmp/run_m1.json`, `/tmp/run_m4.json`에 저장했다. 확인용 사본은 호스트 `/tmp/run_m1.json`, `/tmp/run_m4.json`에 있다.
- 손실 주입 실행 JSON은 coordinator 컨테이너 `/tmp/run_m1_loss10.json`, 호스트 `/tmp/run_m1_loss10.json`에 있다.
- 테스트용 clone은 `/tmp/fsslk-pipeline-test`이고 Compose 서비스는 보고서 작성 시점에도 실행 중이다. 종료 명령: `cd /tmp/fsslk-pipeline-test && docker compose down`.

## 현재 구현 범위

### `main`에 반영된 기능

- CPU Coordinator/Worker 클러스터, heartbeat와 상태 조회, CPU 텐서 분산 합산.
- 길이 접두 프레임과 raw tensor payload 전송(`int64`, `float32`, 최대 프레임 64 MiB).
- CPU 처리량 및 네트워크 probe 측정과 이를 반영하는 결정적 청크 스케줄링. `sum` 작업 청크는 최대 3회까지 재시도한다.
- Docker Compose의 fast/medium/slow 양방향 네트워크 프로필.
- `fsslk.wrap`을 통한 PyTorch forward graph 캡처, FLOPs·텐서 크기 분석, 두 stage 분할점 보고. `main`의 graph 기능은 아직 캡처와 분석 단계이며 Worker에서 실행하지 않는다.

### `pipeline-exec`에만 있는 기능

- 제한된 연산 allowlist에 따른 그래프/인자 직렬화, stage 명세 검증과 Worker 실행.
- 두 Worker로의 stage 및 가중치 배포, activation 전달, 두 stage의 마이크로배치 실행 중첩, 실행 시간·오차 보고 및 JSON 저장.
- 현재 실행 경로는 단일 텐서 입력, 두 stage와 두 Worker에 한정되며, 허용된 연산과 CPU wire dtype(`int64`, `float32`)만 처리한다.
- end-to-end 정상 실행은 확인했지만, 이 브랜치에는 새 자동화 테스트가 추가되지 않았고 README에도 `run-pipeline` 안내가 없다. 따라서 기능은 동작 확인됐으나 `main` 병합 전 검증과 문서 보강이 남아 있다.

### 아직 구현되지 않은 큰 범위

- 일반 PyTorch 모델 전체 지원, GPU 실행, 학습/autograd 및 동적 제어 흐름.
- 파이프라인 장애 복구·stage 재시도, 여러 stage/worker를 자동 배치하는 runtime.
- 텐서 압축·양자화·캐싱, PyTorch ProcessGroup/backend 통합, 자동 최적화.
- Worker 인증 및 통신 암호화.
