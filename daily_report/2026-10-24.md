# FSSLK 작업 기록 — 2026-10-24

## 오늘 한 일

### 분산 작업과 네트워크 측정 개선

- 길이 접두 프레임으로 JSON 메타데이터와 텐서 바이너리를 전송하도록 구성했다. CPU `int64` 및 `float32` 텐서를 지원하고 프레임 크기를 64 MiB로 제한한다.
- Worker 시작 시 CPU 합산 처리량을 측정한다. Coordinator는 RTT와 jitter, 전송 처리량, UDP probe 패킷 손실률 및 연결 안정성을 수집해 `status`에서 보여준다.
- 측정된 CPU 성능과 RTT, 네트워크 처리량 및 손실률을 반영해 작업 청크를 나누는 결정적 스케줄러를 구현했다. 강화학습은 사용하지 않는다.
- Worker 연결이 끊기거나 작업이 실패·타임아웃되면 청크를 다른 Worker에 재시도하고, 최대 시도 횟수를 넘으면 요청을 실패 처리한다. 이전 시도의 늦은 응답은 무시한다.

### Docker별 네트워크 프로필

Compose에서 Worker마다 Linux `netem` 설정을 다르게 적용했다. 송신은 `eth0`, 수신은 IFB로 리다이렉트해 양방향을 모두 제한한다.

| Worker | 지연 | 속도 상한 | 패킷 손실 |
|---|---:|---:|---:|
| fast | 2 ms | 500 Mbps | 0% |
| medium | 25 ms | 50 Mbps | 1% |
| slow | 75 ms | 10 Mbps | 3% |

- `git diff --check`를 통과했다. 검증 후 `docker compose down`으로 클러스터를 종료했고, `docker compose ps --all`에서 실행 중인 컨테이너가 없음을 확인했다.

## 현재 제한 사항

- 패킷 손실은 UDP probe로 측정한다. TCP 데이터의 전송 복구는 TCP 자체 재전송에 맡기며, 애플리케이션 수준 재시도는 현재 stateless `sum` 작업의 청크 단위로 동작한다.
- 스케줄러는 현재 측정치를 사용하는 휴리스틱이다. 손실에 따른 처리량 보정도 단순 모델이므로 실제 작업과 네트워크 환경에 맞춘 보정이 필요하다.
- 인증과 암호화는 구현하지 않았다.

## `pipeline-exec` 브랜치 검증 (아직 `main`에 미병합)

- `origin/pipeline-exec`의 `28c684c`를 별도 clone에서 확인했다.
- 변경분은 캡처 그래프를 허용된 PyTorch 연산 목록으로 직렬화하고, 두 stage로 나눠 Worker에 정의와 가중치를 배포한 뒤 activation을 마이크로배치로 흘려보내는 기능이다. Coordinator는 stage 요청을 지정 Worker에 전달하며, CLI에 `run-pipeline`을 추가했다.
- 해당 브랜치에서 `python -m unittest discover -s tests -v`를 실행해 44개 테스트가 통과했다. Docker Compose로 실제 coordinator와 Worker 3개도 올렸고 모두 `active`로 등록됐다.
- 병합 준비 단계에서 bundle, stage 명세/runtime, Worker stage 수명주기, Coordinator relay와 binary reply, 파이프라인 출력·마이크로배치·배포 실패 정리 테스트 15개를 추가했다. `run_pipeline`이 0회 반복을 명시적으로 거부하도록 검증도 보강했다. 업데이트한 브랜치 작업 트리의 전체 59개 테스트가 호스트와 README의 Docker 명령에서 모두 통과했고 `git diff --check`도 통과했다. Docker에서는 NumPy 미설치 PyTorch 경고가 나왔지만 테스트에는 영향이 없었다.
- 자동 미분의 첫 단계로 `StageRuntime.run_with_grad`와 일회성 `StageExecution.backward`를 추가했다. stage 하나의 floating input/weight gradient를 반환하고, 두 stage 사이에 activation gradient를 수동 전달하는 결과가 일반 PyTorch autograd와 일치하는지 검증했다. 직접 작성한 matmul stage와 캡처된 Linear 모델의 gradient를 비교하는 테스트 4개를 추가한 뒤 호스트와 Docker에서 전체 63개 테스트가 통과했다. 현재 StageSpec은 trainable parameter와 floating buffer를 구분하지 않아 floating `params` 전체를 gradient target으로 다룬다.
- 컨테이너 hostname을 Worker ID로 사용해 기본 데모 모델(4 layers, dim 512, heads 8, batch 8, sequence 256)을 실행했다. m1과 m4 모두 결과 검증을 통과했다.

## 현재 구현 범위

### `main`에 반영된 기능

- CPU Coordinator/Worker 클러스터, heartbeat와 상태 조회, CPU 텐서 분산 합산.
- 길이 접두 프레임과 raw tensor payload 전송(`int64`, `float32`, 최대 프레임 64 MiB).
- CPU 처리량 및 네트워크 probe 측정과 이를 반영하는 결정적 청크 스케줄링. `sum` 작업 청크는 최대 3회까지 재시도한다.
- Docker Compose의 fast/medium/slow 양방향 네트워크 프로필.
- `fsslk.wrap`을 통한 PyTorch forward graph 캡처, FLOPs·텐서 크기 분석, 두 stage 분할점 보고. `main`의 graph 기능은 아직 캡처와 분석 단계이며 Worker에서 실행하지 않는다.

### `pipeline-exec`에만 있는 기능

- 제한된 연산 allowlist에 따른 그래프/인자 직렬화, stage 명세 검증과 Worker 실행.
- 두 Worker로의 stage 및 가중치 배포, activation 전달, 두 stage의 마이크로배치 실행 중첩, 실행 시간·오차 보고 및 JSON 저장.
- 로컬 stage runtime에서 autograd forward와 backward gradient 계산. 아직 Worker 프로토콜을 통한 backward 전달은 아니다.
- 현재 실행 경로는 단일 텐서 입력, 두 stage와 두 Worker에 한정되며, 허용된 연산과 CPU wire dtype(`int64`, `float32`)만 처리한다.
- README에 `run-pipeline` 실행법, microbatch 동작, 제한 사항과 stage-level autodiff API의 범위를 추가했다. 자동 테스트와 문서가 보강된 변경은 `pipeline-exec`의 별도 작업 트리에 있으며 아직 `main`이나 원격 브랜치에는 병합·push되지 않았다.
- Coordinator에서 A→B activation payload를 임시 파일로 spool하고, 대기 queue를 1개로 제한해 B가 느릴 때 A에 backpressure를 건다. B가 파일 bytes를 읽으면 decode 전에 파일을 삭제하고 실행 종료 시 남은 임시 디렉터리도 정리한다. 의도적으로 느린 B 테스트에서 읽는 중·대기 중·producer가 넣는 중인 파일을 합해 동시에 3개를 넘지 않는 것을 확인했다. `FSSLK_ACTIVATION_SPOOL_DIR`로 spool 디스크 경로를 지정할 수 있다.
- 이 spool은 대기 중인 activation이 RAM에 계속 쌓이는 문제를 줄인다. 하지만 프레임 수신 시 payload 전체가 먼저 메모리에 올라오고, 활성 microbatch 및 최종 출력도 메모리가 필요하다. 프레임당 64 MiB 제한도 그대로이므로, 메모리보다 큰 단일 activation을 처리하려면 streaming 전송과 tile-aware stage 연산이 추가로 필요하다.
- Coordinator spool 및 정리 테스트를 더한 뒤 전체 65개 테스트가 호스트와 Docker에서 모두 통과했다.
- Worker heartbeat를 stage 데이터 연결과 분리한 별도 TCP control 연결로 옮겼다. Worker는 등록 시 받은 control token으로 연결하고 순번이 있는 heartbeat를 보내 ACK를 확인하며, control 연결이 끊기면 지수 backoff로 재접속한다. Coordinator 상태는 `healthy`·`suspect`·`unreachable`로 나누고, `suspect`는 lease 절반부터, `unreachable`은 `max(설정 timeout, heartbeat 간격 × 3)` 이후로 판정한다. 새 작업은 healthy worker에만 보내며 lease가 만료되면 해당 worker의 pending RPC를 실패 처리한다.
- Heartbeat 채널 등록·토큰 검증·ACK·재접속·상태 전이·pending RPC 만료 테스트를 추가했다. 전체 70개 테스트가 호스트와 Docker에서 통과했다. Compose 실제 실행에서 Worker 3개가 모두 healthy로 등록됐고, Worker 하나를 pause했을 때 suspect→unreachable로 바뀐 뒤 unpause 후 healthy로 회복됐다. `run-sum --size 16`은 pause 전후 모두 기대값 120과 일치했다.
- 기존 `pipeline-exec` 작업물을 복사한 `refactor-pypi` 브랜치와 `/tmp/fsslk-refactor-pypi` worktree를 만들었다. 원래 `pipeline-exec` 작업 트리는 유지했다. PyPI/공식 문서 기준으로 Ray, gRPC, `torch.distributed.pipelining`, safetensors, DiskCache를 비교한 내용은 새 브랜치의 `docs/pypi-refactor-options.md`에 기록했다. 첫 선택지는 현재 네트워크 실험 구조를 유지하는 gRPC transport/health spike이며, MNIST 분산 학습을 위해 PyTorch pipeline도 별도 비교할 후보로 남겼다. 이번 조사에서는 의존성을 설치하거나 런타임을 바꾸지 않았다.

### 아직 구현되지 않은 큰 범위

- Worker 간 backward 전달, loss/optimizer, gradient 집계와 데이터셋 처리 등 분산 학습 경로. 현재 autograd는 stage 안에서만 동작한다.
- 일반 PyTorch 모델 전체 지원, GPU 실행 및 동적 제어 흐름.
- 파이프라인 장애 복구·stage 재시도, 여러 stage/worker를 자동 배치하는 runtime.
- 텐서 압축·양자화·캐싱, PyTorch ProcessGroup/backend 통합, 자동 최적화.
- Worker 인증 및 통신 암호화.
